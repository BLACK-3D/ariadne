# Ariadne without Codex

On Windows, double-click **Start Ariadne.cmd**. The small launcher starts a hidden, independent host, waits for readiness, opens the local console and exits. Starting it again reuses the verified host. Codex and the launcher window can then close. Pairing uses the existing local key in `data/server.token`; the background log never prints that key.

**Stop Ariadne.cmd** requests a graceful server shutdown, closes its local voice/briefing/agent services and releases the model and fixed flow service trees that this host created. It checks the host's executable, Windows owner SID and process creation time before signaling a random local Windows event. It never terminates a process by a stale PID, adopts an unknown existing service, or force-kills an unresponsive host. Stop may interrupt active work, as closing a foreground server does; stop an idle box when preserving an in-progress mission matters.

The default launcher explicitly requests Windows job breakaway. If the calling environment denies it, same-user Windows CIM process creation starts the same fixed isolated Python entry point outside the caller's process job. Both routes verify the new process's immutable identity and its launch-specific readiness receipt. There is no ordinary inherited-child fallback. If Windows denies both routes, startup fails with an explanation rather than claiming independence. This does not weaken any capability worker's CPU/memory/process job.

The host strips inherited API keys, proxy variables and Python hooks. Only reviewed non-secret Ariadne configuration fields survive, and host data remains inside the box. Its request records, status, logs and locks live in `data/host`. Each newly created Ollama/flow tree belongs to a separate host-lifetime job, so stopping or losing the host also releases those services. Explicit owner-configured external model services keep their own lifecycle.

On the supported Windows 10/11 host, service creation uses `STARTUPINFOEX` with an atomic job list. The model/flow process belongs to its lifecycle job before its initial thread runs, so an early descendant or a host crash cannot escape an assignment window. Only duplicated standard-input/output/error handles are inherited. Failure to establish those attributes refuses creation; no suspended/uncontained fallback is used. Stop is signaled before status persistence, so a full disk or sharing failure cannot disable shutdown. A missing final stop receipt is reported honestly rather than treated as a complete confirmation.

No Windows service, startup-folder entry, Task Scheduler entry, registry setting, firewall setting or administrator installation is added. The existing 6 AM wake task is unchanged. Ariadne must still be started after Windows reboot/sign-out unless a separately authorized OS startup arrangement exists. A power outage cannot keep software running without electrical power; existing files and recovery records survive according to the filesystem and previous backup arrangements.

When migrating from an already-running foreground instance, first let its work become idle, preserve its listening/brief preferences and stop its verified old processes. The independent launcher refuses a conflicting foreground server or preexisting model/flow service. It does not silently relabel an inherited process as independent. `scripts/launch.py --no-browser` remains available for explicit foreground operation on supported platforms; `start.sh` keeps its existing behavior.

Validation uses disposable loopback HTTP children inside controlled kill-on-close Windows jobs: the normal control child dies when its parent exits, while the explicit breakaway and CIM fallback children remain reachable and accept explicit graceful stops. This proves process-job independence under those tested conditions, not reboot persistence or a physical Codex-close test. Production takeover and fresh-folder application startup have separate receipts.

Additional native fixtures create an immediate service descendant, verify both processes belong to the exact owned job, then confirm both exit after explicit job closure and abrupt owner death. An invalid-job fixture confirms failure without runnable service code. These fixtures do not load a model or change any capability worker's accepted resource limits.
