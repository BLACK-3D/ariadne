# Checked private backups · 0.13

Double-click **Backup Ariadne.cmd**. This local utility creates a uniquely named ZIP in `backups/`, checks every archived member and database snapshot, and saves a verification receipt next to it. The console waits for the result. No server restart, microphone access, network request, model call, recurring service or Windows task is involved.

The backup contains private owner data and access keys. It is not encrypted. Keep the archive and receipt private, including when copying them to separate protected storage. A backup on the same physical drive does not protect against that drive failing.

## What is preserved

The seven known SQLite databases include missions, approval history, memories, imported documents, business/survival records, routine definitions and runs, brief receipts and public Internet cache/history. Routines and settings live in the main database; they do not need a separate routines database.

The existing explicit configuration allowlist is retained, including pairing and flow tokens, HTTP/MCP registrations, capability profiles, knowledge vectors and the optional ERP bootstrap environment. Regular, singly linked workspace files include generated briefs and procedure reports. The archive's manifest binds every included member to its exact byte count and SHA-256.

Models, runtime engines, speech weights, source files, logs, host process status, stop-event capabilities, PID/lock files, browser profiles and arbitrary files outside the workspace/configuration allowlist are excluded. Fixed factory flow definitions are regenerated by the launcher. These backups complement a separately preserved full offline appliance; they do not replace it. Custom capability paths or credentials supplied through environment variables need separate owner arrangements.

## What verification means

Each database is copied with SQLite's backup API. The new archive is read back in full: member names, declared sizes, hashes and the exact manifest/member set must agree. Database snapshots are materialized only in a temporary local directory and checked with SQLite's `quick_check`, using read-only connections, disabled trusted schema, bounded work and no extension loading. Temporary material is then removed. The final ZIP name is published exclusively only after these checks pass; existing backups are never overwritten.

Verification rejects legacy archives without the new manifest. It rejects unsafe paths, duplicate/case-colliding names, encrypted or unsupported ZIP entries, link/special-file metadata, undeclared members, changed bytes and invalid databases. It does not run workspace content, execute flows, import application state, call connected systems or launch recovered work.

The hash manifest detects accidental corruption and mismatched files. It is not a signature: someone able to rewrite the backup and its manifest can replace both. A passed structural check does not prove a document's accuracy, complete application recoverability or the absence of harmful content.

Limits are 10,000 members, 1 GiB per database/workspace member, 16 MB per configuration member and 8 GiB total expanded payload. The manifest is limited to 2 MB and ZIP directory metadata to 16 MB before parsing. Operations have a 300-second deadline and individual SQLite checks/backups have 30-second deadlines. Traversal also has count and depth bounds. A limit failure produces no success claim; a large installation may require a separately reviewed archival plan.

For maintainers, the schema-1 consistency marker and warning strings are part of the archive format. Preserve that contract when editing future prose, or provide explicit versioned-format compatibility.

## Live snapshot limits

Each SQLite snapshot is consistent individually. Databases, configuration and workspace files are copied sequentially, so the result is **not one global point-in-time transaction**. Concurrent files can change; detected changes cause failure rather than a success claim. Unsafe linked/special workspace entries are omitted and counted in the evidence. Unsafe database/configuration inputs cause failure.

For a coordinated database-and-workspace snapshot, let work settle and stop Ariadne deliberately before backing up. The utility never stops or pauses it automatically. Backing up and reading the archive use CPU, storage bandwidth and temporary disk space; there are no model/API charges. No measured energy or monetary savings are claimed.

Windows capture pins existing database and sidecar files against rename while allowing ordinary SQLite writes, and validates their opened handles. A present rollback journal causes capture to fail before pinning it, so the utility does not prevent a live writer from completing journal cleanup. Retry after writes settle. Missing sidecars are checked before and after capture without being created. POSIX retains checked descriptors but does not prevent another process owned by the same user from renaming paths. These controls do not isolate the box from a privileged local attacker or provide a filesystem-wide snapshot.

## Verify again, fully offline

From this box's folder, with the actual archive filename:

```powershell
.\runtime\python\python.exe -I -B scripts\backup_box.py --verify backups\ariadne-private-TIMESTAMP-ID.zip
```

For scripting and a JSON receipt:

```powershell
.\runtime\python\python.exe -I -B scripts\backup.py --verify backups\ariadne-private-TIMESTAMP-ID.zip --temp-root backups --json
```

Create a new explicitly named backup with the existing command interface:

```powershell
.\runtime\python\python.exe -I -B scripts\backup.py backups\owner-snapshot.zip --json
```

The box controls ignore inherited data-directory overrides and use this folder's `data/`. The lower-level command honors an explicit `ARIADNE_DATA_DIR` without creating a pairing key. Neither command restores data. Verify-only does not initialize an owner database or token.

## Recovery remains a deliberate owner action

Preserve current state before attempting recovery, verify a trusted backup, and inspect it in a fresh allowed directory with Ariadne stopped. Retain compatible model/runtime assets and review absolute paths separately. Do not extract an arbitrary archive over a running installation.

Saved schedules, queued missions, external registrations, approvals and microphone preferences are preserved as data. Starting a restored installation can make that saved authority active again. Review those settings and uncertain/interrupted work before resuming; verification never clears holds, rewrites history or replays actions. The current local flow runtime also uses the original box's fixed `data/flows` path, so changing `ARIADNE_DATA_DIR` is not a complete runtime relocation procedure.

There is no automatic restore or recovery startup in this release. A full application restore and a physical network-disconnected outage test remain separate qualification tasks.
