# Speech repository assessment

Checked 2026-10-28. Public, read-only repository and official documentation research. No repository was cloned, no package/model was installed or executed, no microphone was used, and no deployment or E: access occurred. This is a candidate assessment, not a security audit or a hardware qualification.

## Recommendation

1. **Evaluate sherpa-onnx first as an optional local speech runtime.** Its actively maintained Windows support, configurable keyword spotting, VAD, streaming/non-streaming ASR, and TTS cover more of a local assistant's speech needs. Start with CPU-only VAD and keyword spotting; load larger recognition/synthesis models on demand. This would leave the 16 GB GPU available to the main language model. That is an architectural recommendation, not a measured power or latency improvement on this machine.
2. **Do not bundle openWakeWord's supplied wake models into a general business-capable distribution as though they were permissively licensed.** Code is Apache-2.0; the project's supplied pretrained wake models are CC-BY-NC-SA-4.0. A custom classifier requires separate training-data, synthesis-model, embedding, and redistribution license checks. Merely training a new name does not establish clearance.
3. **Treat ONNX Runtime as a dependency, not a speech system or a sandbox.** Pin the exact tested runtime/model combination and inventory native dependencies. A newer standalone ONNX Runtime release does not prove that a sherpa build includes it or that replacing its DLL is compatible.

## sherpa-onnx

The official repository documents local speech recognition, synthesis, speaker functions, VAD, keyword spotting, enhancement, and source separation. Windows x64, x86, and arm64 are listed; C/C++, Python, C#, JavaScript, and other language APIs are available. Windows documentation provides CPU build instructions and precompiled packages. Windows GPU support also exists in the current source/build workflows; GPU acceleration is unnecessary as a starting assumption for a small always-on detector. See [repository](https://github.com/k2-fsa/sherpa-onnx), [Windows installation](https://k2-fsa.github.io/sherpa/onnx/install/windows.html), and [GPU dependency configuration](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/cmake/onnxruntime-win-x64-gpu.cmake).

The runtime's own code is [Apache-2.0](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/LICENSE). **That is not a blanket license for model weights, datasets, voices, dictionaries, or every bundled native dependency.** The official [VAD documentation](https://k2-fsa.github.io/sherpa/onnx/vad/index.html) explicitly distinguishes MIT Silero VAD from TEN VAD's modified Apache license and asks users to check model licenses. Silero's upstream [README](https://github.com/snakers4/silero-vad) and [license](https://github.com/snakers4/silero-vad/blob/master/LICENSE) affirm MIT licensing. That makes Silero a clearer first VAD component to qualify; it does not license unrelated sherpa models.

Sherpa's [keyword spotting documentation](https://k2-fsa.github.io/sherpa/onnx/kws/index.html) supports changing configured keywords without retraining. Threshold and keyword boost affect false triggers and misses. Its [pretrained model page](https://k2-fsa.github.io/sherpa/onnx/kws/pretrained_models/index.html) documents the bilingual `sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20`, 160 ms chunk-8 and 320 ms chunk-16 model latency, and quantized graphs. Published graph sizes include a 4.4 MB int8 encoder, 743 KB decoder, and 85 KB int8 joiner; these are disk file sizes, not process RAM or energy measurements. The page supplies a Windows executable invocation and an example with CPU provider and one thread. Algorithmic chunk latency is not full microphone-to-action latency.

**KWS weight-license gap:** The official sherpa KWS documentation/release asset metadata reviewed here did not expose a separate model license. The model author's [ModelScope model page](https://www.modelscope.cn/models/pkufool/icefall-kws-zipformer-zh-en-3M-2025-12-20) did not return readable content through the available browser tool. Third-party mirrors claiming Apache-2.0 are insufficient primary evidence for redistribution clearance. Record the original author's license and the phoneme dictionary/test-audio licenses before selecting this artifact for a distributable bundle. No claim of cleared KWS redistribution is made here.

## openWakeWord

The stable [v0.6.0 README](https://github.com/dscripka/openWakeWord/blob/v0.6.0/README.md) documents local ONNX inference on Windows. Input is 16-bit 16 kHz PCM; multiples of 80 ms trade latency against processing efficiency. The [stable implementation](https://github.com/dscripka/openWakeWord/blob/v0.6.0/openwakeword/model.py) creates CPUExecutionProvider sessions with intra/inter-op thread counts of one. Optional Speex noise suppression is documented for x86/arm64 Linux, not as a supported Windows enhancement.

The README's Raspberry Pi 3 example says one core can run 15–20 wake models in real time. This is a maintainer performance claim, not a Windows benchmark, idle-watt measurement, or guarantee for arbitrary microphones and wake phrases. Its false-trigger/miss targets and comparative examples depend on threshold tuning, small test sets, and preparation; the authors themselves urge local evaluation. Do not generalize them into an Ariadne reliability claim.

Licenses are explicit in the README's [license section](https://github.com/dscripka/openWakeWord/blob/v0.6.0/README.md#license): code Apache-2.0, included pretrained models **CC-BY-NC-SA-4.0**, attributed to restrictive or unknown training data licensing. The architecture description separately identifies the Google speech embedding backbone as Apache-2.0. This does not remove the supplied wake-classifier restrictions. A supplied `hey_jarvis` model is therefore not a default business-distribution choice.

The [v0.5.1 asset release](https://github.com/dscripka/openWakeWord/releases/tag/v0.5.1) holds the model files referenced by the current package: `hey_jarvis_v0.1.onnx` 1,271,370 bytes, `embedding_model.onnx` 1,326,578 bytes, `melspectrogram.onnx` 1,087,958 bytes, and optional `silero_vad.onnx` 1,807,522 bytes. The supplied wake classifier still has the above noncommercial condition. These byte counts are not RAM requirements. The inspected API returned no asset digest for this release; compute and retain local hashes during a separately authorized provisioning step.

Stable [setup.py](https://github.com/dscripka/openWakeWord/blob/v0.6.0/setup.py) permits broad dependency ranges (`onnxruntime>=1.10.0,<2`, SciPy, scikit-learn, requests, tqdm). Its training extra includes an old TensorFlow CPU stack and other training dependencies. For an inference appliance, exclude unused training extras and produce a tested, hashed platform lock; do not use an unbounded fresh install as the deployment contract. Main-branch requirements differ from the release (including minimum Python version), so pin the chosen ref rather than combining main documentation with stable code accidentally.

## ONNX Runtime and low idle cost

ONNX Runtime code is [MIT](https://github.com/microsoft/onnxruntime/blob/v1.31.1/LICENSE); model licenses remain separate. Its current [threading documentation](https://onnxruntime.ai/docs/performance/tune-performance/threading.html) explains that default CPU sessions may create threads across physical cores and enable spinning, consuming more cycles and power. Thread count and spinning can be configured. For an always-on small detector, evaluate a small explicit CPU thread count and disabled/bounded spinning against detection latency. These settings are candidates to measure, not claimed savings; a wrapper must expose the needed controls.

Standalone [Windows x64 1.31.1 ZIP](https://github.com/microsoft/onnxruntime/releases/download/v1.31.1/onnxruntime-win-x64-1.31.1.zip): 82,929,944 bytes, official asset SHA-256 `5869e26bb25314375f2d5ef1877e3ea06b1543d6c710e6e4a1ec2f7177ab4b2c`. This is not the same artifact as sherpa's pinned 1.28.2 build. No model, package, or runtime was executed here.

## Security evidence and limits

At the checked GitHub security pages, [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx/security) and [openWakeWord](https://github.com/dscripka/openWakeWord/security) report no detected SECURITY.md and no published repository advisories. This means neither a clean bill of health nor absence of privately reported/upstream issues. Sherpa has Windows build/test workflows and a manually triggered sanitizer workflow; openWakeWord has Python 3.10 Windows/Linux tests. Workflow presence alone does not prove a particular release passed, an external audit occurred, or an installed dependency set is safe.

[ONNX Runtime's security policy](https://github.com/microsoft/onnxruntime/blob/main/SECURITY.md) routes vulnerability reports to MSRC and describes coordinated disclosure. Its repository security page also showed no published repository advisories, while [official releases](https://github.com/microsoft/onnxruntime/releases) describe memory, input-validation, external-data path, and dependency security fixes. Do not interpret an empty repository advisory list as absence of security maintenance or CVEs elsewhere. This assessment did not perform an exhaustive vulnerability-database or binary scan, and located no independent audit certification for either speech project in the reviewed official materials.

The official [ONNX Runtime model-validation documentation](https://onnxruntime.ai/docs/#model-validation) warns that conforming models can still exhaust memory or compute and advises inspecting/testing untrusted models safely. Native inference workers should receive only pinned, selected model files, bounded audio, resource/deadline limits, and no unnecessary account credentials or outbound access. KWS output is an untrusted activation signal; it must not itself authorize spending, publication, accounts, privileged actions, or irreversible tools. No microphone or ambient-listening behavior should start as a side effect of research or provisioning.

## Local evidence still required

Before selecting a speech upgrade, obtain primary licenses/notices for every exact artifact and dependency, then test the packaged build offline on the target Windows system. Measure cold start, steady-state RAM/VRAM, CPU use and wall power at idle/listening/transcribing, wake latency, misses, false activations during realistic background audio, cancellation, device failure/reconnection, and network-disconnected startup. Compare against the existing push-to-talk/offline transcription path. No numerical operating-cost reduction, 16 GB fit guarantee, voice accuracy threshold, or production-readiness acceptance is established by this research alone.
