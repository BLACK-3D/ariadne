# Automation repositories for Ariadne

Verified: **2026-10-28**. Scope: official project repositories, release pages, documentation, licenses, and selected published advisories for three candidates. This is a capability and deployment assessment, **not a security audit**. No repository was cloned, installed, or executed. No external accounts, devices, or production services were connected. Release observations are a dated snapshot; a deployment must check advisories again against its exact pinned versions.

## Recommendation

Keep Ariadne's small local runtime and deterministic tools as the default appliance. Add external automation engines as optional, separately operated services when a concrete workflow needs their integrations. A single application with broad credentials, arbitrary code, and unrestricted networking would expand both authority and maintenance cost.

| Candidate | Best use | Priority for Ariadne | Principal constraint |
| --- | --- | --- | --- |
| [Home Assistant Core](https://github.com/home-assistant/core) | Local device state, energy/environment telemetry, reviewed device actions | First device integration; begin with selected reads | Authenticated users are a trusted boundary; device/cloud dependencies vary |
| [Activepieces](https://github.com/activepieces/activepieces) | Owner-authored business workflows and reusable integrations | First workflow-engine candidate to qualify, optional | MIT core/commercial feature split; sandbox, egress, replay, and package provisioning require explicit configuration |
| [n8n](https://github.com/n8n-io/n8n) | Existing n8n installations or a required connector absent elsewhere | Conditional alternative; avoid bundling by default | Source-available license restrictions, code-runner isolation, and a larger optional Assistant stack |

These priorities are architectural judgments for this product, not measured rankings of project security or performance. Installing all three would duplicate scheduling, execution history, credential storage, updates, and backups without an established need.

## Home Assistant

**Maintenance and license.** GitHub's latest release resolved to [Core 2026.10.4, released October 24](https://github.com/home-assistant/core/releases/tag/2026.10.4). The [October release notes](https://www.home-assistant.io/blog/categories/release-notes/) and [full changelog](https://www.home-assistant.io/changelogs/core-2026.10) show an active monthly release line and integration/dependency maintenance. Core uses [Apache-2.0](https://github.com/home-assistant/core/blob/dev/LICENSE.md); redistribution must also account for included components, notices, and trademarks.

**Local deployment and costs.** The project supports its own OS, containers, and VMs. Its [installation guide](https://www.home-assistant.io/installation/) recommends Home Assistant OS for most users and documents Windows through an OS VM; Container does not include OS-managed apps. Do not replace this PC's OS to add it to Ariadne. An optional separate VM/service fits better. Offline usefulness must be established per chosen device/integration; local operation of the hub does not make cloud-dependent devices work without the internet. Its integration metadata distinguishes [IoT communication classes](https://contributors.home-assistant.io/core/integrations/manifest/#iot_class).

Storage has an ongoing cost: [Recorder](https://www.home-assistant.io/integrations/recorder/) writes state changes, recommends SQLite by default, and documents retention/filtering and storage wear concerns. Exclude noisy entities and choose history retention deliberately. The site's Raspberry Pi minimum is not a measured RAM budget for a VM sharing this PC with an LLM. No local energy or memory benchmark was performed.

**Authority and security.** The [security policy](https://www.home-assistant.io/security/) accepts reports against current official stable/development versions, uses private GitHub disclosure, and explicitly assumes every authenticated user is trusted with owner-like access. A non-admin account must not be treated as a robust isolation boundary for an AI integration. The policy's published fixes also distinguish components: for example, the critical host-network app exposure was fixed in **Supervisor 2026.03.2**, not simply by assuming a Core version covers every component.

The current [MCP integration](https://www.home-assistant.io/integrations/mcp_server/) initially exposes all LLM APIs, including APIs added later, and requires an administrator account by default. It can instead select individual APIs and exposed entities. This convenience is broader than Ariadne needs initially.

**Proposed integration.** Build a small owner-configured gateway for explicit entity IDs and fixed operations. Start with bounded state reads; return observed timestamps and unavailable/stale states. Keep the HA credential outside model context. For writes, bind Ariadne approval to the entity, exact service/action and parameters, and gateway configuration revision. Do not expose a generic service caller or broad MCP tool list. Test with virtual entities before connecting hardware. Treat locks, alarms, heating, valves, and power controls as a separate qualification scope.

## Activepieces

**Maintenance and license.** GitHub's latest release resolved to [0.92.3-hotfix.1, October 23](https://github.com/activepieces/activepieces/releases/tag/0.92.3-hotfix.1), explicitly updating Node.js for October security fixes. Other maintained release branches also received hotfixes; a date-sorted hotfix is not necessarily the intended product release. The [license documentation](https://www.activepieces.com/docs/about/license) identifies MIT core and commercial enterprise/cloud features, including the `ee` trees. Confirm every required governance/API/embedding feature against the chosen edition rather than assuming the whole repository is MIT or every documented control is free.

**Local deployment and costs.** The current [self-host guide](https://www.activepieces.com/docs/install/options/docker-compose) describes an app, worker, PostgreSQL, and Redis; it specifies Docker Compose v2, at least 2 vCPU/4 GB RAM, and WSL2 on Windows. These are vendor setup requirements, not a local benchmark. Preserve the connection encryption key with database backups; backing up the source folder alone does not back up Docker data. Review the shipped worker count instead of accepting it as this PC's workload size.

The [single-container hobby setup](https://www.activepieces.com/docs/install/options/docker) uses PGLite and an in-memory queue, but the project warns that it cannot scale or migrate to Enterprise without starting over. That tradeoff is poor for business runs needing durable outage recovery. Free core licensing does not remove costs of local compute, backups, updates, or paid external services.

**Isolation.** The [sandbox documentation](https://www.activepieces.com/docs/install/architecture/sandboxing) distinguishes code isolation from process isolation. `SANDBOX_CODE_ONLY` avoids privileged containers and arbitrary npm in Code steps; `UNSANDBOXED` is unsuitable for untrusted workflow authors. Process-based modes require substantial host capabilities. Ariadne should not gain a Docker socket or privileged worker merely to expose integrations. Validate behavior against the selected release: documentation and execution mechanisms evolve.

Networking is independent. [Network Security](https://www.activepieces.com/docs/install/architecture/network-security) says `AP_NETWORK_MODE` defaults to `UNRESTRICTED`; `STRICT` adds an application-level SSRF guard. The project explicitly describes that guard as best-effort and bypassable by deliberately malicious code, requiring infrastructure egress enforcement for a strong boundary. Use narrowly permitted service destinations; do not allowlist an entire LAN simply to reach one local API.

**Security history and maintenance duty.** The [security policy](https://github.com/activepieces/activepieces/security) provides private disclosure and a response process; it explicitly scopes unsandboxed deployments as trusted-operator use. Selected published issues demonstrate why version pinning and regression checks matter:

- [GHSA-m992-8rcw-vmrx](https://github.com/activepieces/activepieces/security/advisories/GHSA-m992-8rcw-vmrx): optional queue dashboard authentication regression in 0.80.0–0.84.0; fixed 0.84.1. It was exposed only when that dashboard was enabled. Keep this administrative surface disabled unless needed.
- [GHSA-gr3h-c2j7-r52g](https://github.com/activepieces/activepieces/security/advisories/GHSA-gr3h-c2j7-r52g): Code-step top-level module loading escaped the V8 isolate through 0.79.4; fixed 0.80.0. A sandbox label alone is insufficient evidence that every execution path is contained.

**Offline and replay qualification.** [Piece syncing](https://www.activepieces.com/docs/install/architecture/piece-syncing) is hourly cloud-registry reconciliation by default; individual flow steps pin exact piece versions. An air-gapped appliance must provision and verify every required piece/dependency in advance and prove a cold restart/run with external networking unavailable. [Environment settings](https://www.activepieces.com/docs/install/reference/environment-variables) also show telemetry enabled initially, with an instance setting controlling it after initialization. Confirm both persisted settings and network behavior.

Candidate settings to verify on the pinned build are `AP_PIECES_SYNC_MODE=NONE` after provisioning, `AP_CLOUD_AUTH_ENABLED=false` for independently configured connections, `AP_ENABLE_FLOW_ON_PUBLISH=false` to separate publishing from activation, and `AP_ENFORCE_CONNECTION_PIECE_BINDING=true`. The last two defaults are respectively true and false in the current [reference](https://www.activepieces.com/docs/install/reference/environment-variables). These switches support the proposed policy; they do not replace its broker enforcement or prove offline readiness.

[Crash recovery guarantees](https://www.activepieces.com/docs/install/guarantees/crash-recovery) apply to a specified production configuration. A step in flight at failure may repeat an external side effect even though checkpointed steps are skipped; Redis durability remains the operator's responsibility. Reconcile writes after an uncertain result, use provider idempotency keys, and retain a stable operation ID across retries.

**Proposed integration.** Qualify a single reviewed workflow that reads mock inventory and creates a local draft artifact. Ariadne receives an operator-registered flow ID, immutable revision/digest, input schema, declared side effects, and permitted credential references. It may propose draft workflows as artifacts; publishing, credential changes, and enabling recurring runs stay owner operations. A broker must reject changed revisions and unknown inputs. A UI piece catalog hiding an action is not adequate authorization: the [piece-management guide](https://www.activepieces.com/docs/admin-guide/guides/manage-pieces) says hidden pieces can remain in running or published flows.

## n8n

**Maintenance and license.** GitHub's latest stable observation was [2.45.5, released October 28](https://github.com/n8n-io/n8n/releases/tag/n8n%402.45.5). It is actively maintained, with a private disclosure route and current [published advisories](https://github.com/n8n-io/n8n/security). Its [Sustainable Use License](https://github.com/n8n-io/n8n/blob/master/LICENSE.md) permits internal-business/personal uses but restricts providing/distributing the software commercially; enterprise code has separate terms. This is source-available, not an unrestricted open-source dependency. Do not assume that selling or embedding an Ariadne appliance containing n8n is covered; establish license fit before packaging it for others.

**Local deployment and costs.** The current [Compose guide](https://docs.n8n.io/deploy/host-n8n/install-options/install-using-docker-compose.md) includes n8n's own Assistant sandbox and search services, at least 4 GB RAM/2 vCPU, and a **privileged Docker-in-Docker runner**. It describes that bundled sandbox as suitable for local development/testing and recommends a different production sandbox provider. Importing this stack would add authority and operational responsibilities beyond an integration adapter. Do not copy it wholesale into Ariadne. Running fixed workflows without n8n's Assistant is a distinct, smaller scope that must be configured separately.

**Code and network boundaries.** [Task-runner documentation](https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners.md) warns that internal-mode runners share n8n's host identity and can expose credentials/database material if escaped; sensitive production installations need external runners. [Hardening guidance](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/harden-task-runners.md) includes separate containers, unprivileged identity, read-only root, limited temporary storage, and optional host confinement. [Node exclusions](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/block-specific-nodes.md) can completely prevent loading command/file nodes. Keep these excluded; disabling them in a visual editor is weaker. [SSRF protection](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/enable-ssrf-protection.md) should supplement network controls, with tightly scoped internal-service exceptions.

Two relevant advisories were published on the verification date:

- [GHSA-9p7v-45m2-wxgj](https://github.com/n8n-io/n8n/security/advisories/GHSA-9p7v-45m2-wxgj): deprecated Function/Function Item/LangChain Code paths could execute outside Code-node task-runner isolation. Fixes include 2.42.6/2.43.3/2.44.0 and 3.0.1, but previously saved workflows can continue unchanged. Inventory existing workflows and keep deprecated nodes blocked.
- [GHSA-9qx8-fhxv-w794](https://github.com/n8n-io/n8n/security/advisories/GHSA-9qx8-fhxv-w794): optional Browser Use upload resolved arbitrary paths on the n8n server; its approval showed the page host without gating the file path. Fixes include 2.45.5/2.46.1/3.0.1. Leave Browser Use disabled in this integration. The general lesson for Ariadne is to approve the exact file content/path and destination together, and stage only confined artifacts for browser upload.

**Ongoing operation.** [Telemetry](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/control-telemetry.md) and version-notification calls are enabled by default and have separate opt-outs. An offline claim still requires a network-denied test. [Execution retention](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/manage-execution-data.md) is configurable and pruning is enabled by default, but running/waiting/annotated executions have different retention behavior. Keep evidence needed for business reconciliation separately from disposable payload-heavy run logs. No local CPU, RAM, storage, or energy comparison was measured.

**Proposed integration.** Prefer connecting an owner's already maintained n8n service through the same fixed-workflow broker contract proposed for Activepieces. Do not expose a general workflow-creation API, instance admin API, arbitrary credential selection, browser uploads, command execution, or file access to the model.

## Concrete next slice and acceptance evidence

The following is an Ariadne implementation proposal, not a claim about features already delivered by these projects:

1. Define one adapter contract for a registered operation: service identity; immutable workflow/config revision; bounded input/output schema; read/write classification; exact target; credential-reference names; idempotency/reconciliation strategy; timeout; output redaction; and an owner stop control. Approval fingerprints include all action-changing fields. Store credentials outside model-visible output.
2. Implement a local mock service and two operations: selected-state/inventory read, and create-draft output. Test disallowed targets, revision changes after approval, unknown fields, prompt injection in returned data, secret-bearing errors, redirect destinations, duplicate delivery, timeout after a committed write, power-loss recovery, and stop/re-enable behavior. No real business write is needed to establish this contract.
3. Qualify **one** optional platform only when its connector set solves an actual requirement. For device work choose Home Assistant; for new general workflows start with Activepieces CE if the required feature set is licensed and works in its reviewed isolation mode. Use n8n when existing ownership/connectors justify its license and operation requirements.
4. Freeze tested images/packages with digests, retain notices and a dependency inventory, export reviewed flow revisions, and document a restore procedure. Store all Ariadne-associated files/volumes on approved storage inside the accepted Yikes layout; **E: remains excluded**. WSL/Docker defaults need an explicit storage-location review before any later installation.
5. Demonstrate cold boot and a complete selected workflow with internet disconnected, then simulate a crash around a write and reconcile it without an unapproved duplicate. Include the router/switch, radio hubs, target device power, and any essential local DNS in the outage test.
6. Measure idle RAM, active peak RAM, p50/p95 completion time, disk/log growth per 1,000 runs, external requests and model tokens per run, restore time, and wall power on the actual box. Report scenario/concurrency and uncertainty. Deterministic workflows can avoid an LLM call for routine repeated steps, but the magnitude of savings is **unmeasured**. Additional upfront adapter/reliability work is distinct from recurring compute, energy, licensing, and maintenance cost.

Published advisories demonstrate concrete failure modes and update requirements. Their count, severity mix, or absence does not establish comparative project security. No recommendation here authorizes installation, spending, publication, external writes, or broader autonomous authority.
